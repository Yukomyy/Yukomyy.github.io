01 / CONTEXT

Overview & Problem Statement

Project Overview

Small and mid-sized operational units frequently outgrow shared spreadsheets when managing purchasing and warehouse stock. This project implements a core Enterprise Resource Planning (ERP) procurement and inventory module designed around an immutable stock movement ledger rather than mutable quantity columns.

Problem Statement

When multiple staff record goods receipts and stock issuances concurrently, directly updating a single `quantity_on_hand` column leads to lost updates, unexplainable inventory variances, and zero historical visibility into stock levels at a specific date.

02 / DESIGN GOALS

Objectives & Engineering Solution

Key Objectives

  • 01Model an append-only `stock_ledger_entries` table where current stock is deterministically derived from signed movement deltas.
  • 02Enforce a strict procurement state machine: Draft Requisition → Approved PO → Partial/Full Goods Receipt → Ledger Posting.
  • 03Prevent concurrent over-allocation using database row-level locking (`SELECT ... FOR UPDATE`) inside serializable transactions.
  • 04Provide clear audit trails showing who approved or adjusted every stock movement.

Solution Summary

I architected a full-stack TypeScript application backed by PostgreSQL. Instead of mutating item counts destructively, every goods receipt, outbound issuance, or cycle-count adjustment writes an immutable ledger record paired with a cached snapshot balance updated atomically within the same SQL transaction.

04 / IMPLEMENTATION

Selected Code & Query Logic

The core engineering guarantee lives in the stock movement transaction service. Before recording an outbound issuance, the service acquires a row lock on the warehouse item balance, checks sufficiency, records the ledger entry with a reference document ID, and updates the balance.

src/services/inventoryLedger.tstypescript
export async function postStockMovement(
  tx: Prisma.TransactionClient,
  input: {
    skuId: string;
    warehouseId: string;
    deltaQty: number; // positive for receipt, negative for issuance
    referenceType: "PO_RECEIPT" | "ISSUANCE" | "ADJUSTMENT";
    referenceId: string;
    actorId: string;
  }
) {
  // 1. Acquire row-level lock on current stock balance
  const [balance] = await tx.$queryRaw<Array<{ qty_on_hand: number }>>`
    SELECT qty_on_hand
    FROM warehouse_stock_balances
    WHERE sku_id = ${input.skuId} AND warehouse_id = ${input.warehouseId}
    FOR UPDATE
  `;

  const currentQty = balance?.qty_on_hand ?? 0;
  const nextQty = currentQty + input.deltaQty;

  if (nextQty < 0) {
    throw new Error(`Insufficient stock for SKU ${input.skuId}: available ${currentQty}, requested ${Math.abs(input.deltaQty)}`);
  }

  // 2. Insert immutable audit ledger record
  await tx.stockLedgerEntry.create({
    data: {
      skuId: input.skuId,
      warehouseId: input.warehouseId,
      deltaQty: input.deltaQty,
      balanceAfter: nextQty,
      referenceType: input.referenceType,
      referenceId: input.referenceId,
      createdById: input.actorId,
    },
  });

  // 3. Upsert materialized balance snapshot
  return tx.warehouseStockBalance.upsert({
    where: { skuId_warehouseId: { skuId: input.skuId, warehouseId: input.warehouseId } },
    update: { qtyOnHand: nextQty },
    create: { skuId: input.skuId, warehouseId: input.warehouseId, qtyOnHand: nextQty },
  });
}
05 / ENGINEERING TRADE-OFFS

Challenges & Architectural Decisions

Technical Challenge

Calculating stock balances on the fly with `SUM(delta_qty)` vs. storing a mutable `qty_on_hand` column.

Engineering Decision

Implemented a hybrid Snapshot + Ledger pattern updated inside a single ACID transaction.

Trade-off Accepted

Slightly higher write overhead per transaction in exchange for O(1) balance reads and a complete historical audit trail.
