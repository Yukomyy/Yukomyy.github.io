01 / CONTEXT

Overview & Problem Statement

Project Overview

Scheduling shared physical resources (computer labs, seminar rooms, and hardware kits) requires strict temporal validation. This full-stack web platform replaces ad-hoc messaging forms with a centralized availability calendar, automated conflict detection, and status tracking.

Problem Statement

Checking time-slot overlaps only in frontend JavaScript fails when two users submit overlapping intervals simultaneously or when partial-hour bookings overlap existing reservations.

02 / DESIGN GOALS

Objectives & Engineering Solution

Key Objectives

  • 01Enforce conflict-free time intervals in PostgreSQL so overlapping approved bookings are mathematically impossible.
  • 02Deliver a fast, accessible timetable interface usable on both desktop monitors and mobile devices.
  • 03Provide clear status transitions (`Pending`, `Approved`, `Rejected`, `Cancelled`) with conflict previews for lab coordinators.

Solution Summary

I combined a clean Next.js + TypeScript frontend with a PostgreSQL backend utilizing `tstzrange` interval checks and GiST exclusion constraints. Users can filter labs by capacity and equipment, inspect live daily/weekly grids, and submit structured reservation requests.

04 / IMPLEMENTATION

Selected Code & Query Logic

Using PostgreSQL's `btree_gist` extension, the database itself rejects any attempt to approve two reservations for the same room whose `[start_time, end_time)` intervals overlap.

sql/migrations/002_booking_exclusion_constraint.sqlsql
CREATE EXTENSION IF NOT EXISTS btree_gist;

CREATE TABLE room_reservations (
    reservation_id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    room_id        UUID NOT NULL REFERENCES rooms(room_id),
    requester_id   UUID NOT NULL REFERENCES users(user_id),
    purpose_title  TEXT NOT NULL,
    time_slot      TSTZRANGE NOT NULL,
    status         TEXT NOT NULL CHECK (status IN ('PENDING', 'APPROVED', 'REJECTED', 'CANCELLED')),
    created_at     TIMESTAMPTZ NOT NULL DEFAULT NOW(),

    -- Prevent any two APPROVED reservations for the same room from overlapping
    CONSTRAINT no_overlapping_approved_bookings
    EXCLUDE USING gist (
        room_id WITH =,
        time_slot WITH &&
    ) WHERE (status = 'APPROVED')
);
05 / ENGINEERING TRADE-OFFS

Challenges & Architectural Decisions

Technical Challenge

Allowing multiple pending requests for the same slot while preventing multiple approved bookings.

Engineering Decision

Used a partial GiST exclusion constraint (`WHERE (status = 'APPROVED')`) paired with automatic conflict warnings on pending items.

Trade-off Accepted

Coordinators can review competing requests before approving one, while the database guarantees final consistency.

What I Learned

Date and time-range logic is notoriously error-prone when written as nested `if/else` statements. Leveraging native interval types (`[)` half-open ranges) simplifies both backend queries and UI rendering.
