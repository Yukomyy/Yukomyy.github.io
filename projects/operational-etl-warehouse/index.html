01 / CONTEXT

Overview & Problem Statement

Project Overview

Analytical reporting slows down dramatically when analysts must join 8+ normalized operational tables and manually merge flat files every week. This project implements a structured Medallion / Kimball data warehouse architecture that separates raw ingestion (`raw`), cleaned conformance (`staging`), and business-ready dimensional marts (`mart`).

Problem Statement

Re-running naive ingestion scripts created duplicate rows whenever a pipeline failed midway, and silent upstream schema changes broke downstream charts without warning.

02 / DESIGN GOALS

Objectives & Engineering Solution

Key Objectives

  • 01Ensure every pipeline run is strictly idempotent—re-running the same date partition produces the exact same warehouse state.
  • 02Design a Kimball Star Schema with surrogate keys and Slowly Changing Dimension (SCD Type 2) tracking for historical accuracy.
  • 03Halt pipeline execution automatically if null primary keys, orphan foreign keys, or negative metric values are detected.

Solution Summary

I built a containerized Python + PostgreSQL pipeline structured around three schemas (`raw`, `stg`, `mart`). Ingestion loads batch files into staging tables using content hashes, SQL transformation scripts merge records using `INSERT ... ON CONFLICT DO UPDATE`, and a quality-gate runner verifies row counts and constraints.

03 / SYSTEM DESIGN

Architecture, Workflow & Stack

Three-tier data warehouse pipeline with idempotent upserts and automated quality gates.

01 / Bronze (Raw)

Batch Extract & Hash Tagging

Loads source CSV/JSON payloads with ingestion timestamps and SHA-256 row hashes.

02 / Silver (Staging)

Type Casting & Deduplication

Standardizes UTC timestamps, trims identifiers, and deduplicates using `ROW_NUMBER() OVER (PARTITION BY natural_key)`.

03 / Gold (Mart)

Dimensional Star Schema & Assertions

Populates `dim_*` and `fct_*` tables and executes post-load SQL assertion checks.

04 / IMPLEMENTATION

Selected Code & Query Logic

To guarantee idempotency when updating the fact table for a given date partition, transformations deduplicate staged records and perform an atomic upsert keyed on the business transaction key.

sql/mart/upsert_fct_operations.sqlsql
INSERT INTO mart.fct_service_operations (
    operation_natural_key,
    date_key,
    entity_sk,
    service_sk,
    processing_duration_sec,
    total_cost_idr,
    record_hash,
    updated_at
)
SELECT
    s.operation_id AS operation_natural_key,
    TO_CHAR(s.completed_at_utc, 'YYYYMMDD')::int AS date_key,
    de.entity_sk,
    ds.service_sk,
    s.processing_duration_sec,
    s.total_cost_idr,
    s.record_hash,
    NOW()
FROM stg.stg_operations_deduped s
INNER JOIN mart.dim_entity de
    ON s.entity_code = de.entity_code AND de.is_current = TRUE
INNER JOIN mart.dim_service ds
    ON s.service_code = ds.service_code
WHERE s.partition_date = :target_date
ON CONFLICT (operation_natural_key)
DO UPDATE SET
    processing_duration_sec = EXCLUDED.processing_duration_sec,
    total_cost_idr          = EXCLUDED.total_cost_idr,
    record_hash             = EXCLUDED.record_hash,
    updated_at              = NOW()
WHERE mart.fct_service_operations.record_hash <> EXCLUDED.record_hash;
05 / ENGINEERING TRADE-OFFS

Challenges & Architectural Decisions

Technical Challenge

Handling historical changes when an organizational unit changes its department classification.

Engineering Decision

Modeled `dim_entity` with `valid_from`, `valid_to`, and `is_current` columns (SCD Type 2).

Trade-off Accepted

Adds complexity to dimension joins (`BETWEEN valid_from AND valid_to`), but preserves accurate historical attribution.

06 / OUTCOMES & RETROSPECTIVE

Results & What I Learned

Verifiable Outcomes

  • ✓Zero duplicate fact records across repeated backfill tests on identical date partitions.
  • ✓Simplified downstream BI queries from 7-table operational joins to single-hop star schema joins.
  • ✓Automated detection of schema drift and null key violations prior to mart publication.

What I Learned

Data engineering is fundamentally about trust and recoverability. Pipelines will eventually encounter malformed input; designing idempotent loads and explicit quality gates makes recovery routine instead of an emergency.
